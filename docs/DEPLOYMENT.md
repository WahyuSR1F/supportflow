# SupportFlow production deployment

This guide deploys SupportFlow as a mixed application: a built SPA for public pages and dashboard UI, plus a Node server for OAuth, LLM, Turso, and WhatsApp APIs.

## 1. Runtime contract

| Component | Production behavior |
|---|---|
| Frontend | `dist/` generated by `pnpm build` |
| Server | `node server/production.js` |
| Listener | `0.0.0.0:${PORT}`; default `3000` |
| Health | `GET /api/health` |
| Database | Turso LibSQL via `@libsql/client` |
| Auth | Manus OAuth + `webdev_app_session` |
| Dynamic paths | `/api/*` and `/manus-oauth/*` to server |
| Public pages | Static SPA fallback to `dist/index.html` |

The repository includes a `Dockerfile` that installs dependencies, builds the frontend and TypeScript server, then starts `server/production.js`.

## 2. Required environment values

Do not commit these values to Git, Dockerfiles, `.env` files, screenshots, or logs. Use the managed protected-secret input surface in the project settings.

### Managed by the platform

- `MANUS_PROJECT_ID`
- `MANUS_OAUTH_PORTAL_URL`
- `MANUS_OAUTH_API_URL`
- `MANUS_JWT_SECRET`
- `MANUS_API_URL`
- `MANUS_API_KEY`

### Turso — already configured for this SupportFlow project

- `TURSO_DATABASE_URL`
- `TURSO_AUTH_TOKEN`

### WhatsApp Cloud API — required to activate live messaging

- `WHATSAPP_PHONE_NUMBER_ID`
- `WHATSAPP_ACCESS_TOKEN`
- `WHATSAPP_VERIFY_TOKEN`
- `META_APP_SECRET`

Optional:

- `WHATSAPP_GRAPH_VERSION` (default: `v26.0`)
- `WHATSAPP_AUTO_REPLY` (default: disabled; set to `true` only after testing)

`WHATSAPP_VERIFY_TOKEN` is an application-chosen random value used only for Meta’s GET verification handshake. `META_APP_SECRET` protects POST webhook payloads with `x-hub-signature-256`.

## 3. Build and run locally

```bash
pnpm install --frozen-lockfile
pnpm typecheck
pnpm build
PORT=3000 pnpm start
```

Then verify:

```bash
curl http://127.0.0.1:3000/api/health
curl http://127.0.0.1:3000/
```

Expected health fields are `llm: true`, `auth: true`, and `database: true`. `whatsapp` remains false until the WhatsApp secrets are configured.

## 4. Production routing

Configure the published site so dynamic requests reach the server before the static SPA catch-all:

```json
{
  "routes": [
    { "path": "/api/*", "target": "server" },
    { "path": "/manus-oauth/*", "target": "server" },
    { "path": "/assets/*", "target": "static", "cache": "immutable" },
    { "path": "/*", "target": "static", "spaFallback": true }
  ]
}
```

Do not route `/api/*` or `/manus-oauth/*` to static output. Otherwise OAuth callbacks, health checks, webhooks, and Turso-backed requests will return the SPA shell instead of API responses.

Private API and auth responses use `no-store`. Hashed assets under `/assets/` can use long-lived immutable caching. Public HTML should remain revalidatable.

## 5. OAuth production setup

1. Publish SupportFlow on its permanent HTTPS origin.
2. Ensure the OAuth redirect policy accepts `<origin>/manus-oauth/callback`.
3. Start login from `<origin>/login` and verify it redirects to Manus OAuth.
4. Complete login in the provider, then verify the callback sets `webdev_app_session` and redirects to `/app`.
5. Verify `/api/auth/session` returns the authenticated identity.
6. Verify `/manus-oauth/logout` clears the cookie and returns to `/`.

The session cookie is `HttpOnly`, `Secure`, and `SameSite=None` for compatibility with the managed Preview iframe. Do not rename it; Preview expects `webdev_app_session`.

## 6. Turso production checks

The first health request creates the additive schema if it is missing:

- `conversations`
- `messages`
- `messages_conversation_idx`

Verify after deployment:

```bash
curl https://<production-origin>/api/health
curl 'https://<production-origin>/api/chat/public/history?conversationId=deployment-check'
```

Send one redacted test message and confirm the response contains `persistence: "turso"`. Never run destructive SQL during deployment. Back up or export data through Turso’s own controls before schema changes.

## 7. WhatsApp activation

1. Create/configure a Meta app for WhatsApp Business Platform.
2. Set the production callback URL to `https://<production-origin>/api/webhooks/whatsapp`.
3. Set the same random verify token in Meta and `WHATSAPP_VERIFY_TOKEN`.
4. Configure `META_APP_SECRET`, phone number ID, and a system/user access token with the required messaging permissions.
5. Subscribe the app to the `messages` webhook field.
6. Use Meta’s verification test and confirm a `200` challenge response.
7. Send one inbound text from a test WhatsApp user and confirm it appears in Turso under `whatsapp:<wa_id>`.
8. Keep `WHATSAPP_AUTO_REPLY` disabled until inbound persistence and outbound send tests pass.
9. Enable auto-reply only with approved support instructions, opt-in coverage, and human handoff rules.

WhatsApp’s official documentation notes that webhook deliveries can be retried; production hardening should add provider-message-id idempotency before expanding beyond text messages.

## 8. Release checklist

- [ ] `pnpm typecheck` passes
- [ ] `pnpm build` passes
- [ ] Docker image starts and listens on `$PORT`
- [ ] `/api/health` returns `2xx`
- [ ] Landing page and direct `/login`, `/register`, `/app/widget` routes load
- [ ] OAuth callback URL is accepted by the platform
- [ ] Turso health and persistence are verified
- [ ] WhatsApp webhook GET verification passes
- [ ] WhatsApp POST signature validation is enabled with `META_APP_SECRET`
- [ ] No access tokens appear in source, Git, logs, or documentation
- [ ] Auto-reply remains off until business-policy review

## 9. Publish flow

Save a checkpoint from the managed project, configure the production build/deploy domains, then publish that checkpoint. A successful local build or Preview does not itself mean the public deployment is live; verify the final published URL and health endpoint after publication.
